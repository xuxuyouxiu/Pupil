## 1. 问题陈述

**谁**：重度使用 AI 编程 Agent 的开发者（个人或团队）。

**什么场景**：开发者同时并行运行 2-6 个甚至更多 Agent 会话（Claude Code、Codex CLI、Hermes、dsh、自研 Harness 等），任务动辄运行数分钟到数小时。开发者把任务挂到后台，切去写代码、开会、看文档。

**什么痛点**：
1. **错过完成时机**：Agent 十分钟前就完成了，人还在干别的，白白浪费等待时间。
2. **不知道卡没卡**：Agent 在等权限批准或已静默报错，终端里"等待输入"和"正在思考"看起来一模一样，必须逐个切换终端标签页去读输出才能分辨。社区把这个问题叫"tab-hunting"（标签页狩猎）——六七个终端标签，一个一个点开找哪个在等你，一天十几次，每次 30 秒。
3. **多任务并行顾此失彼**：一个会话卡在批准提示 10 分钟无人发现，你以为所有 Agent 都在干活，实际上只有一个在动。
4. **工具割裂**：每个 CLI 工具的通知能力各自为政，自研 Harness 完全没有通知；现有监控工具大多绑定单一生态。

**现在怎么解决的、为什么不行**：
- 手写 hook 脚本弹系统通知（PowerShell / osascript / notify-send）：一次性方案，通知太多时无法分辨是哪个会话，不展示持续状态，每个工具要单独配置。社区文章原话："一个会话一条通知可以，五个并行会话就变成一堆分不清的提示音"。
- tmux 分屏 / 标签命名：能看到多个会话但每格太小，仍需逐格肉眼读输出；"等待"和"思考"在终端里没有视觉区分。
- 官方多会话面板（如 Claude Code Agent View）：需要主动切回终端打开查看，不是常驻的余光可见状态，且只覆盖自家会话。
- macOS 菜单栏/灵动岛类工具：只支持 macOS，Windows 用户无解。

## 2. 产品定位

**一句话定位**：Windows 优先的开源桌面悬浮球，用余光感知所有 AI Agent 的实时状态——在跑、在等、出错、完成，一眼分清，关键事件主动找到你。

**定位说明**：
- 形态：常驻屏幕左侧的小体积半透明置顶悬浮球（Grok 式黑色球体 + 两只动画眼睛），平时安静待着，事件发生时眼睛表情变化/外环变色/提示音/系统通知。
- 泛化：不绑定任何单一 Agent。数据接入采用"事件协议 + 适配器"开放架构，官方适配器覆盖主流 CLI 工具，任何自研 Harness 都能按协议接入。
- 轻量：低资源占用是产品级承诺（非目标而是约束），常驻后台不打扰其他应用。
- 开源：面向个人开发者与团队分享场景，本地优先，默认不上传任何数据。

## 3. 目标用户

### 主要画像：AI 重度开发者「并行多会话的操盘手」
- 年龄 25-40，资深开发者 / 独立开发者，Windows 10/11 工作环境。
- 日常并行运行 2-6 个 Agent 会话：Claude Code 跑重构、Codex 跑测试、dsh 跑部署验证，长任务挂后台自己继续写代码或开会。
- 技术水平高，愿意装一个工具并做少量配置（装适配器/hook），但对"又一个 Electron 内存大户"极度反感。
- 核心诉求：不用切换窗口就知道每个会话的状态；完成/出错时第一时间被提醒；能区分是哪个工具的哪个会话。

### 次要画像 A：团队技术负责人「统一工具的分发者」
- 带一个 5-20 人的开发团队，团队内混用多种 Agent 工具，且有自研 Harness。
- 核心诉求：一个工具全团队通用（含自研 Harness 接入）、配置门槛低（最好一键装好适配器）、开源可审计、能打包成团队标准配置分发。

### 次要画像 B：自研 Harness 的维护者「接入方」
- 公司或团队内部维护自己的 Agent Harness，无监控无通知能力。
- 核心诉求：有清晰的事件协议规范和接入文档/SDK，花半小时就能让自己的 Harness 被监控起来。

## 4. 用户故事

1. 作为并行运行多个 Claude Code 会话的开发者，我想不切换窗口就知道哪个会话在等我的批准，以便立即处理而不打断手头的工作。
2. 作为挂机等长任务的开发者，我想在任务完成时听到提示音并看到悬浮球变色，以便第一时间回去看结果。
3. 作为同时使用 Claude Code 和 Codex 的开发者，我想在悬浮球上区分每个会话来自哪个工具，以免混淆。
4. 作为 Windows 用户，我想让悬浮球常驻屏幕左侧、半透明、可拖动、不遮挡操作，以便随时用余光感知状态。
5. 作为自研 Harness 团队的负责人，我想按标准事件协议把 Harness 接入悬浮球，以便全团队用同一个监控工具。
6. 作为参加会议的开发者，我想一键开启勿扰模式暂停声音和通知，会后再恢复。
7. 作为遇到任务失败的开发者，我想在 Agent 报错时收到强提醒（颜色变化 + 警示音 + 系统通知），以便尽快回来处理重试。
8. 作为想复盘效率的开发者，我想查看事件历史（每个会话何时开始、完成、超时、报错），以便评估 Agent 任务的真实耗时规律。
9. 作为监控多个会话的开发者，我想点击悬浮球上的某个会话直接跳回对应工具窗口，以便省去找终端标签的时间。
10. 作为对声音敏感的用户，我想自定义各类事件的提示音并支持整体静音，以便按自己的习惯调节提醒强度。

### 5.2 形态参照（非直接竞品但定义了用户预期）

| 产品 | 形态 | 对我们的启示 |

### 5.3 替代方案（用户现在的"凑合办法"）

| 方案 | 工作方式 | 为什么不够好 |
|------|----------|--------------|
| **ntfy 手机推送**（含 ntfy-mcp 集成） | Agent 完成时 curl 一条消息到手机 | 人就在电脑前时，手机震动反而是二次干扰；只有"事件通知"没有"持续状态"——不知道 Agent 卡没卡；依赖外部服务器（公有云或自托管），与本地优先诉求冲突 |
| **手写通知 hook 脚本** | Stop/Notification hook 调 PowerShell / osascript / notify-send 弹系统通知 | 一次性通知不构成界面；多会话并行时"一堆一样的提示音分不清谁是谁"（社区原话）；每个工具单独配置，自研 Harness 要自己从零写 |
| **邮件通知** | 脚本完成后发邮件 | 延迟高、淹没在收件箱噪音里、无持续状态，开发者社区已基本弃用 |

### 5.4 市场空白结论

1. **Windows 优先的精品缺位**：Agent 状态监控工具呈"macOS 扎堆"格局（Irrlicht、cctop、AgentBar、XClaw 全部 macOS only；Agent Pulse 跨平台但重心分散且 macOS 未公证）。Windows 用户是被遗忘的大多数，而 Windows 恰恰是团队开发环境的主流。
2. **开放协议化接入是空白**：Agent Pulse 硬编码六款工具列表；claudectl/Agent View 单生态；Tasklight 有 HTTP 接入但无正式协议规范、无适配器框架、无接入 SDK。**没有任何竞品把"自研 Harness 接入"当作一等公民设计。**
3. **声音通知设计被忽视**：几乎所有竞品只做视觉（颜色/动画）或系统通知，无人做"按事件类型区分音效 + 可自定义 + 可静音"的声音设计——而这是用户明确且合理的需求（余光看不到时，听觉是第二通道）。
4. **轻量化承诺稀缺**：宠物/办公室类是 Electron（重），功能堆叠类（Agent Pulse）复杂度上涨。"常驻不打扰"的工具自己必须先做到轻。
5. **勿扰模式 / 事件历史 / 失败重试提醒**：竞品几乎空白（仅 Agent Pulse 有 SQLite 时间线偏分析向），均是低成本高感知的补位机会。

## 6. 我们的差异化

用户为什么选 Pupil 而不是竞品：

1. **Windows 优先的一等公民体验**：不是移植版，原生 Windows 通知（Toast）、开机自启、系统托盘、多显示器与高 DPI 适配从第一天就是验收标准。
2. **协议驱动的开放接入，不绑定任何 Agent**：定义公开的 Agent 事件协议（会话开始/状态变更/工具调用/完成/失败/等待输入），官方适配器开箱即用（Claude Code、Codex、通用 webhook/CLI），自研 Harness 按协议文档半小时接入。竞品的工具列表是封闭枚举，我们的是开放集合。
3. **听觉通道 + 视觉通道双设计**：不同事件不同音效、音效文件可自定义、整体可静音、勿扰模式一键开关——做到"事件发生时找得到你，你忙碌时打扰不到你"。
4. **真正的轻量承诺**：把资源占用写进非功能需求并公开验收（常驻内存目标 < 100MB、空闲 CPU < 1%），与 Electron 宠物类工具划清界限。
5. **开源 + 本地优先**：默认零遥测、零账号、零云依赖，团队可放心分发。

## 8. MVP 范围

**MVP = F1 + F2 + F7 + F8 四个核心模块，外加三个低成本高感知项（F3 勿扰模式、F4 点击跳转、F5 音效自定义）。**

即：一个能监控多个会话、可扩展接入、会说话（音效+通知）、能跳转、可静音的轻量悬浮球。

**MVP 明确包含**：
- 悬浮球：常驻左侧、置顶、半透明、可拖动、位置记忆、每会话独立呈现（F1）
- 详情面板：悬停/点击展开，显示思考中/当前工具/运行时长/来源（F7）
- 事件通知：四类事件区分音效与颜色 + Windows 系统通知 + 总静音（F2、F5）
- 接入架构 MVP：事件协议 v1 + Claude Code 适配器 + Codex 适配器 + 通用 webhook/CLI 适配器（F8）
- 勿扰模式（F3）、点击跳转（F4）
- 系统托盘常驻、开机自启、退出记忆配置

**MVP 不含（进 Backlog）**：事件历史（F9）、超时检测（F6）、Hermes/dsh 适配器与 SDK（F10）、失败重试提醒（F11）、多显示器增强（F12）、主题自定义（F13）。

> 取舍说明：F9/F10/F11 是用户明确提到"有价值"的补充特性，但均不阻塞核心价值闭环（挂机感知状态 + 事件被提醒 + 跳转回去处理）。MVP 验证的核心假设是："余光感知 + 主动提醒"能否让开发者不再 tab-hunting。补充特性在假设验证后快速跟进，且 F10 依赖事件协议 v1 稳定后再对外开放更稳妥。

## 9. 验收标准（Given / When / Then）

### F1 悬浮球常驻状态显示
- Given 用户已启动应用且至少一个会话被监控，When Agent 开始工作，Then 悬浮球显示该会话的"运行中"视觉状态（外环蓝色旋转弧段 + 球体眼睛进入"专注凝视"表情），并在 1 秒内更新。
- Given 悬浮球显示在屏幕任意位置，When 用户拖动悬浮球到新位置并退出重启应用，Then 悬浮球出现在上次拖动后的位置。
- Given 存在多个被监控会话，When 状态变化发生，Then 每个会话在悬浮球上独立可辨（颜色/标签区分工具来源），最高优先级状态（错误 > 等待输入 > 完成 > 运行中）决定悬浮球整体外观基调。
- Given 悬浮球处于展开态，When 用户点击桌面其他区域，Then 面板收起，悬浮球回到半透明常驻态，不遮挡用户后续操作。

### F2 关键事件通知
- Given 某会话正在运行，When 会话完成/报错/超时/进入等待输入任一事件发生，Then 4 秒内触发：悬浮球对应颜色变化与动画 + 对应事件默认音效 + Windows 系统通知（通知内容含工具名、项目名/会话标识、事件类型）。
- Given 用户在设置中开启总静音，When 任一事件发生，Then 不播放任何音效，但颜色变化与系统通知正常。
- Given 四类事件（完成/超时/报错/等待输入），When 分别触发，Then 默认使用四种可明确区分的音效，用户盲听可分辨事件类型。

### F3 勿扰模式
- Given 用户开启勿扰模式，When 任一事件发生，Then 音效静默、系统通知被抑制，悬浮球以月牙图标指示勿扰状态；颜色/动画变化保留（视觉通道不断）。
- Given 用户设置了定时勿扰（如 1 小时），When 到达结束时间，Then 勿扰模式自动关闭并恢复通知。

### F4 点击跳转
- Given 详情面板中显示会话列表，When 用户点击某会话条目，Then 操作系统焦点切换到该会话所在的终端/IDE 窗口（通过窗口标题/进程匹配）。
- Given 目标窗口已被用户关闭，When 用户点击该会话，Then 显示"窗口未找到"提示（警示图标 + 文案），不崩溃、不跳错窗口。

### F7 详情面板
- Given 悬浮球处于常驻态，When 用户悬停或单击悬浮球，Then 面板展开显示每个会话：来源工具与项目名、当前状态（思考中/调用工具中/等待输入/空闲/错误）、正在调用的工具名称、已运行时长。
- Given 会话正在调用工具，When 工具发生切换，Then 面板显示的工具名在 1 秒内更新。

### F8 接入架构
- Given 用户安装 Claude Code 适配器并启动 Claude Code 会话，When 会话产生生命周期事件，Then 悬浮球实时反映状态，全程无需修改 Pupil 核心代码。
- Given 第三方开发者按事件协议 v1 文档向通用适配器发送标准事件，When 事件到达，Then 悬浮球出现对应新会话并正确显示状态——证明协议对外可用。
- Given 某适配器进程异常退出，When 其他适配器仍在运行，Then 其余会话监控不受影响（适配器隔离）。

### 轻量化验收（MVP 必须达成）
- Given 应用常驻运行（3 个活跃会话、面板收起），持续运行 1 小时，Then 常驻内存 < 100MB、空闲 CPU 占用 < 1%、无内存持续增长趋势。

## 10. 边界条件

- **空状态**：无任何会话被监控时，悬浮球显示灰色休眠态（眼睛闭合并拢 + 缓慢呼吸动画），悬停提示"等待 Agent 会话接入"，并给出适配器安装引导入口。
- **错误状态**：适配器断连/数据源不可达时，对应会话标记为"连接中断"（断链图标），悬浮球出现警示色描边；其余会话不受影响。
- **加载状态**：应用启动后适配器初始化期间，悬浮球显示初始化中状态，不显示错误的"无会话"结论。
- **边界值**：并发 10 个以上会话时，悬浮球聚合显示总数 + 最高优先级状态，详情面板内滚动查看全部；单会话运行超过 24 小时时时长显示格式正确（如"25:13:44"）。
- **并发**：同一工具同时开 5 个会话时，会话标识（项目名+会话 ID 后缀）确保互不混淆。
- **权限拒绝**：Windows 系统通知被用户在系统设置中禁用时，应用检测到并提示引导开启，其余通道（颜色/音效）不受影响。
- **音频缺失**：无音频输出设备或音量为零时，音效播放失败静默降级，不报错弹窗。
- **系统睡眠/恢复**：系统睡眠恢复后，悬浮球与适配器连接自动重连；睡眠期间积压的事件不重放通知风暴（只更新最终状态）。
- **同类工具冲突**：检测到其他工具（如 Agent Pulse）已注册同一 hook 时，给出共存提示而非静默覆盖。

## 12. 数据埋点方案

产品为开源本地优先桌面工具，**默认零遥测**。采用"可选匿名统计（opt-in）+ 本地统计"双轨：

### 匿名统计（用户明确勾选开启后才上报，可随时关闭）

| 事件类别 | 必埋事件 | 说明 |
|----------|----------|------|
| 安装激活 | app_install, first_run | 安装量与激活率 |
| 激活 | first_agent_connected | 用户第一个核心动作：第一个会话被成功监控（产品价值时刻） |
| 使用 | app_start, session_tracked, adapter_enabled | DAU、监控会话数分布、各适配器启用率 |
| 通知 | notification_fired, dnd_enabled | 通知触发量、勿扰模式使用率 |
| 异常 | adapter_error, app_crash | 适配器错误类型分布、崩溃率 |

### 实现要求
- 事件命名规范：`{对象}_{动作}`（如 `adapter_enabled`）。
- 属性仅含：匿名随机安装 ID、应用版本、操作系统版本、事件时间戳。**不上报**：IP、项目名、会话内容、工具调用参数、路径等一切可能含代码或隐私的信息。
- 本地统计（始终可用，不依赖网络）：悬浮球累计监控会话数、事件次数，存于本地配置，用户可在设置中查看与清除。

## 13. 明确不做的范围（Out of Scope，v1）

1. **不做 Agent 任务编排/调度**：不创建、排队、派发任务给 Agent（那是 claudectl / Agent View 的领域）。我们是监控者，不是指挥者。
2. **不做 Agent 内直接交互**：不在悬浮球里批准权限、回复提问（crystl 的方向）。v1 保持只读监控定位，避免与 Agent 工具的交互协议深度耦合。可在 v2 依据用户反馈评估。
3. **不做 token 成本/订阅用量监控**：TokenBar、Agent Pulse 已充分覆盖，且引入定价表维护成本高，与核心价值（状态感知）无关。
4. **不做手机端推送与远程监控**：与本地优先定位冲突；P2 可评估"通过通用 webhook 适配器对接 ntfy"作为社区自助方案，不作为官方功能。
5. **不做云服务、账号体系、团队管理后台**：开源分享场景用安装包/配置文件分发即可。
6. **不做桌面宠物/娱乐化形态**：与轻量定位冲突，信息密度低。
7. **不做 macOS/Linux 完整支持（v1）**：架构预留适配层，正式支持排 v2。
8. **不做 Agent 生成内容的展示与解析**：只消费状态事件，不读取/展示对话内容，规避隐私与安全面。

## 14. 补充特性建议（Backlog 取舍判断）

| 特性 | 判断 | 理由 |
|------|------|------|
| 勿扰模式 | **采纳，进 MVP** | Effort 极低（1）而感知强；会议场景高频刚需 |
| 事件历史 | 采纳，P1 | 复盘价值真实（评估 Agent 任务耗时规律），但不阻塞核心闭环；本地 SQLite 存事件流水即可，勿做成重型分析面板 |
| 失败重试提醒 | 采纳，P1 | 直击"报错被错过"痛点；实现依赖事件历史的基础设施，故排其后 |
| 任务超时检测 | 采纳，P1 | "不知道卡没卡"的兜底方案（无事件驱动也能靠时间阈值发现异常）；阈值必须可配置，默认值保守（30 分钟）避免误报轰炸 |
| 会话统计/每日摘要 | 观察，P2 | Agent Pulse 已做且偏重，先验证核心假设；若用户要求再跟进 |
| 订阅用量/成本 | 不做 | 见 Out of Scope 第 3 条 |
| 团队配置模板导出/导入 | 观察，P2 | 团队分发场景的真实需求，但 v1 用默认配置 + 文档已可覆盖，等有团队用户实际反馈再做 |
| 危险命令护栏 | 不做 | 与监控定位无关，属于安全管控赛道（Agent Pulse 的护栏是重功能） |

## 15. 风险与依赖

| 风险/依赖 | 影响 | 等级 | 应对 |
|-----------|------|------|------|
| Agent hook 生态不稳定：Claude Code hooks 事件格式随版本演进；Codex hooks 需要用户手动信任操作 | 适配器失效导致监控中断 | 高 | 适配器版本化与兼容性测试纳入发布流程；提供"适配器自检"功能快速定位失效原因；协议层吸收工具差异，核心不感知 |
| 无 hook 能力的工具（如部分自研 Harness）无事件源 | 只能靠 transcript 文件监听或进程探测，准确性打折 | 高 | MVP 以有 hook/事件能力的工具为主（Claude Code、Codex、通用 webhook）；文件监听/进程探测作为 P2 补充手段 |
| 强竞品 Agent Pulse 先发且开源 | 功能同质化被稀释 | 高 | 差异化聚焦：Windows 一等公民体验、开放协议（自研 Harness 接入）、区分音效设计、轻量承诺；严禁参考/复制其代码（AGPLv3 传染风险），独立实现 |
| Windows 系统通知与音频策略：焦点助手（Focus Assist）/勿扰规则可能拦截 Toast；独占全屏应用下的置顶行为 | 通知不达、悬浮球不可见 | 中 | 检测系统通知权限与焦点助手状态并引导；全屏应用时悬浮球自动降级为托盘状态灯（行为进验收标准） |
| 自研 Harness 接入依赖外部团队配合 | 协议 v1 设计缺乏真实接入方验证 | 中 | 协议设计阶段即邀请用户方自研 Harness 团队评审；通用 webhook 适配器作为无 SDK 的最低门槛接入方式先行 |
| 置顶悬浮球与用户工作流冲突（遮挡、误点击） | 被卸载 | 中 | 半透明 + 点击穿透可选模式 + 拖动自由定位；"不遮挡正常操作"写入 P0 验收 |
| 轻量目标与技术选型矛盾 | 选型偏重导致资源超标 | 中 | 内存/CPU 预算作为架构评审的硬性否决项（交架构师把关） |

## 16. 附录：名词表

| 名词 | 定义 |
|------|------|
| Agent / Harness | 能自主执行任务的 AI 程序及其运行框架（Claude Code、Codex、Hermes、dsh、自研框架等） |
| 会话（Session） | 一个 Agent 的一次连续运行实例，是监控的最小单元 |
| 适配器（Adapter） | 将特定 Agent 工具的事件转换为标准事件协议的桥接模块 |
| 事件协议 | Pupil 定义的公开事件规范（会话开始/状态变更/工具调用/完成/失败/等待输入等） |
| 悬浮球 | 常驻桌面的置顶小部件，多会话聚合状态的第一展示层 |
| 详情面板 | 悬停/点击悬浮球展开的二级面板，逐会话展示明细 |
| Tab-hunting | 开发者在多个终端标签间逐个切换寻找需要关注的会话的行为（本产品要消灭的核心问题） |
